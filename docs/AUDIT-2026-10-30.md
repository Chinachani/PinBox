# PinBox 1.0.21 审查与修复记录

审查日期：2026-10-30。基线：`71d41a6`（1.0.19）。范围：后端 API、SQLite、离线 IndexedDB、同步、扫码、BOM、导入导出、备份恢复及三平台构建。

## 会影响库存或数据完整性的问题

| 原问题 | 修复后的行为 |
| --- | --- |
| 同步响应丢失后重试，可能重复扣库；重复点击推送也可同时发送同一笔操作 | 每笔离线操作有持久化操作号；业务变更和服务器回执在同一个 SQLite 事务提交；并发重试只记一次 |
| 离线建档撞号会转成更新，覆盖服务器库存 | 返回冲突并保留队列，停止后续相关操作，等待核对 |
| 离线修改直接覆盖其他终端刚修改的字段 | 对修改字段记录原值，服务器核对原值后才应用 |
| 本地库位 ID 被当成服务器 ID，可能重命名或删除错误收纳盒 | 按原库位名称定位，并检查备注冲突，不复用本地 ID |
| 服务器清空或恢复后，旧离线操作仍可能落到新库存上 | 每个服务器数据集有独立标识，恢复、清空和初始化后更换标识，拒绝旧队列 |
| 本地库存、流水、待同步队列分多次事务写入；并发操作可能覆盖库存 | 同一 IndexedDB 事务提交这些记录；写入失败整体回滚；等待事务提交成功才反馈 |
| 离线导入没有进入待同步队列；JSON 导入又采用覆盖语义 | CSV/JSON 统一按订单累计，保留流水和批次，整个文件生成一个可重试的同步操作 |
| 同一订单文件重复导入会重复增加库存 | 按原文件字节计算 SHA-256，服务器与离线同步共享导入凭据；改文件名不绕过防重 |
| CSV 回导丢失数量、型号、品牌、价格、库位等英文字段；零库存会变成 1 | 支持程序导出的英文字段、立创中文字段、零数量、报价、预警线、订单日期及多行引号字段 |
| 源库存 JSON 的两类记录处理不一致，同编号批次会被覆盖 | 兼容 `today_orders` 中文字段和 `historical_inventory` 英文字段；按编号累计，保留批次和逐笔流水 |
| 恢复会丢失项目字段、重编号，部分坏流水被静默跳过 | 恢复前校验全部记录、关联和重复 ID；保留项目、流水及库位 ID；先备份再事务替换 |
| 空数据库备份不能恢复或拉取；拉取直接丢弃未同步操作 | 支持空快照；存在待推送操作时拒绝拉取；下载本地备份同时保存待同步队列和同步元数据 |
| 建档、编辑、导入允许负库存或异常数值，分页 0 可触发异常 | 数量/预警线采用有界非负整数，单价必须为有限非负数，分页参数有明确边界 |
| 并发扣库返回的 previous 和日志可能与实际结果不同，异常后连接未可靠关闭 | 写操作在明确事务中完成，失败回滚并释放连接；并发扣库不会透支 |
| `init_data.py` 运行即删除原库存 | 有数据时默认拒绝覆盖；只有显式 `--reset` 才重建，并先备份 |

## BOM 与界面问题

| 原问题 | 修复后的行为 |
| --- | --- |
| BOM 多行重复使用同一份库存，各行都显示够用 | 按编号在行之间分配可用库存，人工改选后重算所有行 |
| 包含型号或相同阻容值就自动认定可替代，电压冲突仍可能命中 | 明确编号或唯一、封装无冲突的可靠型号才自动匹配；短型号、重复型号与相似规格保留为候选，由用户核对封装、额定值和引脚后选择 |
| `4K7` 被算成 6.8k，微法单位有误，四位以上需求数量被当料号 | 修正规格换算及数量解析，保留整段规格文本 |
| 精确命中可能被低置信候选挤出前三；人工改选未更新品牌及关联行 | 可靠命中固定保留，候选选择后更新品牌、成本、可用库存和缺口 |
| 采购 Excel 表头 7 列，实际写入 6 列，编号/型号/价格整体错位 | 序号单独写入，7 列逐一对应；用户文本按文本导出，避免变成 Excel 公式 |
| 离线 BOM CSV 被按库存 CSV 解析，普通 MPN/Qty 表不能使用 | 离线 BOM 使用独立字段映射，支持 MPN、Qty、位号等字段 |
| 离线分类直接 fetch 服务器接口，找料接口缺失 | 分类统一走数据层；补全离线找料与立创链接接口 |
| 输入 `1.5` 数量被删除小数点，成为 15；标签 `1.5个` 被截成 5 | 严格验证整数字符串，拒绝无效数值，不再默认为 1 或 0 |
| 手输回车同时触发手工输入和全局扫码枪监听 | 输入框只走手工处理，扫码统一防重；连续模式无标签数量时要求人工核对 |
| 摄像头 qrbox 回调把两个数字误当成一个尺寸对象 | 按库中约定的 width、height 参数计算有效扫描区域 |
| 中文标签二维码没有实际启用 UTF-8 编码器 | 明确配置 UTF-8，中文二维码经图像解码回读验证 |
| 快速出库后缓存数量未更新，确认阈值继续使用旧值 | 同步更新列表、详情和扫码卡的库存缓存 |
| Esc/遮罩关闭确认框，等待确认的 Promise 永远不结束 | 所有关闭路径都明确返回取消；确认路径明确返回接受 |
| 搜索响应乱序覆盖新结果；深链参数被二次解码 | 只采用最新搜索响应，去掉重复解码并处理坏标签编码 |
| 原生客户端和远程服务器下载仍走当前网页地址，或二进制响应无法下载 | 导出统一走当前数据层、服务器地址及令牌；原生 HTTP 支持表单上传和二进制下载 |
| PWA 缓存只预存无版本参数 URL，带版本参数的脚本离线可能找不到；断网 API 返回 200 | 静态缓存支持查询参数匹配；断网 API 返回 503；只清理本应用的旧缓存 |

## 配置、构建与可复现验证

- Android 签名文件从版本控制移除，口令从 Gradle 移除；本机使用忽略的私密配置，GitHub Actions 使用四项 Secrets。沿用原签名以支持覆盖升级。
- 清除写死的个人局域网默认服务器地址；不再静默将 HTTPS 降级到 HTTP。自签证书需先让设备信任，或由用户明确选择局域网 HTTP。
- 可通过 `PINBOX_API_TOKEN` 启用服务器访问令牌；网页/原生客户端在数据中心填写。可通过 `PINBOX_ALLOWED_ORIGINS` 指定额外来源，默认阻止其他网站跨源调用业务 API。令牌启用后关闭未认证的 WebSocket 广播。
- 上传限制为 20 MB；CSV 导出处理公式前缀，Excel 按文本写入用户字段；Docker 构建上下文排除真实数据库、证书、签名和 Git 历史。
- Linux/Windows 打包包含前端和版本文件；持久数据保存在普通用户可写位置，避免写入只读的安装目录；独立程序启动后打开浏览器。
- Windows 无控制台打包会使标准输出流为 `None`；启动时补齐流，避免 Uvicorn 日志初始化崩溃，并用隔离子进程模拟验证。
- HTTPS 证书路径支持直接运行和容器运行；自动备份使用唯一文件名，避免同一天的清空或恢复覆盖上一份备份。
- 固定 CI 使用 `npm ci`，测试通过后才构建安装包。更新 tar 以修复 npm audit 报告的漏洞，并用可重复执行的安装脚本处理 Capacitor 6 的导入兼容问题。
- `ci-workflows/build-releases.yml` 与真正执行的 `.github/workflows/release.yml` 同步。

验证命令：

```bash
python -m pytest tests/test_inventory.py -q
npm ci
npm test
npm run test:e2e
npm audit --audit-level=high
npm run cap:sync
```

Python 回归测试使用临时 SQLite 库；JS 测试使用隔离 IndexedDB；浏览器测试用独立临时服务器。Linux 独立程序另做打包启动、静态资源、版本和数据目录检查。本次审查没有导入、重建或修改用户真实库存。

本地验证结果：45 项 Python 回归、15 项 JS 回归、18 项桌面/移动尺寸浏览器测试全部通过，`npm audit` 为 0 漏洞，`cap sync android` 成功。Docker 容器运行及实体设备安装未验证。

## 升级与剩余限制

1. 服务器和客户端一起升级到 1.0.21；升级前分别下载服务器和本地完整备份。新客户端使用 `/api/sync/op`，连接旧服务器时会报错并保留队列。
2. 旧版待推送操作没有操作号，无法证明历史上是否已经入账。新版本会保留并暂停这些操作，其本地备份仍可恢复，需与服务器流水核对。不会给这些操作补一个新号后盲目重放。
3. 冲突会停在队首且保留后续操作。先导出本地备份处理冲突；确认服务器记录完整后，可通过明确确认的本地清空和重新拉取重建本机快照。
4. 导入防重针对完全相同的文件字节。编辑后重新导出的订单文件会有不同摘要，仍需核对订单是否重复；采购记录不自动证明到货状态或实际剩余库存。
5. 原 Android 签名已经存在于公开 Git 历史中。移出当前源码和改用 Secrets 不会撤销历史暴露；本次没有重写公共 Git 历史或轮换签名。真正消除这项历史风险需要安排新签名和客户端迁移。
6. 没有实体手机摄像头、扫码枪和实际安装设备参与验收。浏览器尺寸、扫描回调、中文二维码解码以及安装包构建的结果不能替代硬件实测。
