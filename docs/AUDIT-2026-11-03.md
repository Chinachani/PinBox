# PinBox v1.0.21 全流程审查

审查日期：2026-11-03（Asia/Shanghai）。代码基线：`13b3f0c4029c6de28a28e5cf94fd72951644902f`。219 实际运行版本：1.0.21。

本轮确认 25 项代码或功能缺陷：8 项 P1、17 项 P2。另列部署风险、交互改进和设备验收缺口。这是一份审查结果，以下问题尚未修复；现有 78 项测试通过不足以证明这些操作组合安全。

P1：优先修复，会导致错账、丢失修改、错选器件或向错误服务器写入。P2：常规操作下的功能、数据一致性和可用性问题。每项均给出触发条件、实际结果、位置和建议；没有把假设性的攻击或未做的硬件测试算作已复现问题。

> 后续修复：本文是 1.0.21 的修复前基线。1.0.22 的逐项实现和验收边界见 [全流程修复说明](FIXES-2026-11-03.md)。

## 一、需要优先处理的 8 项问题

### F01 [P1] 在线出入库丢失响应后，重试会再次记账

- 位置：`frontend/js/app.js:894`、`backend/main.py:384`。
- 复现：在线库存 20，出库 3；让请求在服务器执行成功后丢失响应。页面提示失败，用户再次操作。
- 实际：第一次页面返回失败时库存已经是 17；重试后变成 14。离线同步的 `op_id` 保护没有应用到普通在线 `/stock` 请求。
- 建议：所有库存变动在发出前生成并持久化操作号；查询或重试不确定结果时复用同号，服务器在库存事务中记录回执。提交中禁用重复按钮只能降低双击风险，不能解决响应丢失。
- 证据：`browser-probes.json` 的 `lost_response`。

### F02 [P1] 推送期间恢复另一份本地备份，可能静默删除未发送的操作

- 位置：`frontend/js/api.js:143`、`frontend/js/local-api.js:1019`。
- 复现：设备 A 的队列 ID=1 正在推送；响应暂缓期间恢复设备 B 导出的备份，其 ID=1 对应另一笔操作；随后放行 A 的成功响应。
- 实际：推送按数值 ID 删除了 B 的新操作。界面报告成功 1 条，待推送队列为空，但 B 的操作从未发送。本地显示 30 件，已发给服务器的建档数量是 20。
- 建议：恢复、清空、推送和拉取共用跨标签页互斥机制；删除回执时同时校验持久化 `op_id` 与本地数据代次。
- 证据：`local-probes.json` 的 `restore_during_sync`；使用两个独立 IndexedDB 实例的正常备份复现。

### F03 [P1] 扫码请求途中切换模式，会把入库变成出库

- 位置：`frontend/js/app.js:1237`、`frontend/js/app.js:1299`。
- 复现：连续入库模式扫描数量 5 的标签；解析请求返回前切换到连续出库。
- 实际：库存从 20 变成 15，而非 25。防重键使用开始时的模式，实际库存方向却读取返回时的全局 `state.scanMode`。
- 建议：一次扫描绑定开始时的模式和会话号；切换模式、结束扫描或离开页面时取消旧会话尚未提交的结果。
- 证据：`browser-probes.json` 的 `scan_mode_change`。

### F04 [P1] “测试连接”立即改变业务写入目标，却保留旧服务器的页面数据

- 位置：`frontend/js/app.js:2811`、`frontend/js/app.js:2845`、`frontend/js/api.js:78`。
- 复现：先加载服务器 A 的物料 C10001（20 件）；在“服务器地址（同步用）”中填写服务器 B 并测试连接；返回原物料卡点击出库。
- 实际：界面仍显示 A 的型号和 20 件，操作却扣减 B 的同编号物料，B 从 80 变为 79。旧 WebSocket 和详情缓存也没有随连接配置重新初始化。
- 建议：测试连接使用临时配置；明确应用新服务器后统一清空旧页面状态、重建连接、重新加载数据，再开放写入。
- 证据：`browser-probes.json` 的 `server_switch_stale`，两个独立本机服务器复现。

### F05 [P1] BOM 归一化删除小数点，把不同阻值自动认定为同型号

- 位置：`backend/bom.py:260`、`backend/bom.py:498`；离线对应 `frontend/js/local-api.js:191`。
- 复现：库存有 `4.7K`，核对 `47K 2`。
- 实际：返回 `match_tier=norm`、`matched_model=4.7K`、`status=ok`。小数点被删除后两个型号相同，相差十倍的阻值被自动接受。
- 建议：型号归一化保留有电气含义的小数点、后缀和分隔；规格值须独立解析与比较。未知等价关系只能进入候选，不应给出自动命中。
- 证据：`backend-probes.json` 的 `bom_decimal_collision`。无需依赖厂商额定参数即可证明数值不等价；本轮未复核整个用途库的厂商数据手册。

### F06 [P1] 从 BOM 缺料结果建档，会把需求量直接变成实物库存

- 位置：`frontend/js/app.js:2646`。
- 复现：BOM 中不存在的器件需求 10，点击“未找到”建档，补上编号后保存。
- 实际：建档表单预填“入库数量=10”，保存即产生 10 件库存及初始入库流水；没有发生收货或库存清点。再次核对会把原本缺料的物料判作有货。
- 建议：从需求进入建档时库存默认 0；需求量单独展示。真实入库必须由用户另行确认数量和来源。
- 证据：`browser-probes.json` 的 `bom_create_phantom`。

### F07 [P1] 多人在线编辑档案会静默覆盖对方已经保存的字段

- 位置：`frontend/js/app.js:1965`、`backend/main.py:340`。
- 复现：A 打开编辑表单；B 修改备注或价格；A 只改一个其他字段后保存。
- 实际：表单提交全部档案字段，服务端没有版本或原值校验，A 的旧备注/旧价格覆盖 B 的新值。离线同步的 `expected` 冲突保护不适用于普通在线 PUT。
- 建议：仅提交实际修改字段，并对这些字段的原值或记录版本做乐观并发校验；冲突时展示具体差异。
- 证据：`backend-probes.json` 的 `online_edit_overwrite`。

### F08 [P1] 本地备份恢复到服务器后丢失导入凭据，同一订单可再次累加

- 位置：`frontend/js/local-api.js:870`、`backend/main.py:743`。
- 复现：导入订单 5 件并拉取到本地；导出本地完整备份，恢复到服务器，再导入完全相同的订单文件。
- 实际：恢复返回成功，再次导入也返回成功，库存变成 10。离线备份把导入凭据放在 `local_meta`，服务端恢复只读取顶层 `import_receipts`，二者共用相同 `backup_version` 却不互通。
- 建议：统一有版本的备份协议，迁移两种元数据表示；不兼容的来源应明确拒绝，不能悄悄丢失防重状态。
- 证据：`backend-probes.json` 的 `local_backup_receipt_loss`。

## 三、219 部署与安全状态

### D01 部署文件没有完整同步

通过 SSH 只读核对，219 `/mnt/data_sdc1/lcsc-stock-mobile` 的前后端运行代码与审查版本对应，但部署目录没有 `.dockerignore`；`init_data.py` 仍是旧版直接删除并重建库存的脚本；`docker-compose.yml` 也仍是旧版，仅设置 `TZ`，未传入令牌和允许来源配置。

后果：再次执行 Docker 构建时，`COPY . /app` 会把真实数据库、备份和证书加入构建上下文及镜像；按新版说明仅配置 Compose 的 `.env` 也不会使这些变量进入旧容器配置。旧初始化脚本在源数据存在且执行成功时会覆盖库存，没有新版的 `--reset` 闸门及预备份。

建议以固定提交生成完整发布目录、排除业务数据和私密配置，备份后部署；健康检查不仅比版本接口，还要检查配置清单、文件摘要和依赖。不能只复制 backend/frontend/package.json 就视为部署全部完成。

### D02 219 目前未启用 API 令牌

实际容器中 `PINBOX_API_TOKEN` 未设置，匿名读取统计/完整备份成功，服务监听 8088/8089。相同默认配置在隔离环境下可无认证修改库存。CORS 只约束浏览器来源，不能限制同网段脚本、原生客户端或能直达端口的其他终端。

这表示可连接该服务的终端都拥有库存写权限；没有证据表明该端口已经暴露到公网。本轮没有对 219 发送任何库存写入、清空或恢复请求。是否启用令牌应结合可信设备范围落实，并一并解决 F21 的错误反馈。

### D03 Android 历史签名暴露仍未消除

当前版本不再跟踪签名文件，Secrets 已用于 CI，但旧公开 Git 历史中的签名暴露仍在。沿用旧签名能保持覆盖升级兼容，也保留了他人冒用该签名的风险。需要单独制定密钥迁移、旧客户端数据备份及更新方案；从当前树删除文件不等于轮换密钥。

### D04 依赖审计结果已发生变化

- npm：4 个 moderate 条目，0 high、0 critical；涉及 `@capacitor/cli → rimraf → glob → minimatch`，实际根源为 2 个公告，不能说成 4 个独立漏洞。它们主要位于开发/构建依赖链。相关公告：[glob](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4)、[minimatch](https://github.com/advisories/GHSA-g3hv-75wg-m249)。
- Python：对 219 容器实际安装的 31 个包版本审计，`pip 24.0` 和 `setuptools 79.0.1` 命中公告。工具原始输出 15 条，按 ID 去重为 8 个（pip 6、setuptools 2），主要涉及恶意安装包、包索引或构建流程。未据此宣称普通库存 API 存在已验证远程执行漏洞。
- Python 依赖只有下限约束，Docker 基础镜像也未固定摘要；同版本重建不能保证相同依赖。CI 仅审计 npm 且阈值为 high，当前这批 moderate 仍可通过发布门禁；没有 Python/容器镜像漏洞门禁。

建议先核实公告适用条件再升级锁定，保留构建兼容性测试。不要采用 npm 建议的降级 Capacitor 4 来机械“修复”。审计原始 JSON 保存在证据目录；本轮未自动升级依赖。
